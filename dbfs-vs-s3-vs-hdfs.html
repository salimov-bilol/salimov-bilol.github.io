DBFS vs. HDFS vs. S3: Data Storage Architectures 💾

This comparison clarifies the distinct roles and technical specifications of Databricks File System (DBFS), Hadoop Distributed File System (HDFS), and Cloud Object Storage (S3/ADLS/GCS) within the data ecosystem.

Feature DBFS (Databricks File System) HDFS (Hadoop Distributed File System) S3 (Amazon Simple Storage Service)
Core Architecture Abstraction Layer / Mount Point. A service that provides a single interface to a cloud data lake. Distributed File System. A true file system designed to run on dedicated cluster hardware. Cloud Object Storage. A massive, regional service based on a flat namespace (RESTful API).
Data Location Physically stored in the underlying Cloud Object Store (S3, ADLS, GCS). Physically stored on the local disks of the cluster's worker nodes. Stored on Cloud Provider Infrastructure (highly replicated across multiple data centers).
Primary Purpose To provide a unified, file-system-like path (e.g., /dbfs/...) for Databricks users to access the data lake. Designed for low-latency data locality and high throughput for the older Hadoop/MapReduce ecosystem. Designed for scalable, durable, and cost-effective storage; the foundation of a modern data lake.
Data Consistency Inherits Eventual Consistency from the underlying cloud store. (Delta Lake adds ACID on top). Strongly Consistent. Reads are guaranteed to see the most recent write immediately. Eventually Consistent for some operations, though most modern S3 operations are now strongly consistent.
Latency Medium. Depends on network latency to the cloud object store. Very Low. Data is local to the compute cluster. Medium. Higher than HDFS, especially for frequent small file operations.
Fault Tolerance Inherits high durability (99.999999999%) from the underlying cloud store. Achieved by replicating data across multiple worker nodes. Achieved by massive internal replication across multiple Availability Zones.
Cost Model A Databricks platform feature. The actual storage is billed by the cloud provider (per GB, per API request). Requires fixed investment in dedicated compute/storage hardware. Pay-as-you-go for storage and data transfer. Excellent cost-efficiency for archive and storage.
